# Phase 4 scoring methodology

## Status

The scoring implementation remains under verification. It reads the operational PostgreSQL schema and stores immutable score-run configuration, supplier scores, component rows, and source evidence. Delivery and cost calculations have database-independent scenario unit tests; their current SQL readers and persistence paths still require PostgreSQL verification.

## Run configuration

The configured weights are Delivery 25%, Quality 20%, Cost 15%, Capacity 15%, Compliance 10%, and Disruption 15%. The current default window is 365 days and minimum eligible weight coverage is 70%. Eligible component weights are renormalized by their sum. Missing, insufficient, or invalid observations are not assigned zero component scores. Classifications use 90/80/65/50 boundaries.

## Intended component formulas

- Delivery: valid non-DRAFT, noncancelled PO lines due within the inclusive window and known by the cutoff. Calculate OTIF from cumulative shipment quantities, with completion time from cutoff-valid delivery events. Keep completed on-time/late rates, partial quantity, overdue outstanding quantity, and excluded/cancelled line counts separate. See `component-definitions.md` for denominators and status policy.
- Quality: accepted inspected units / valid inspected units × 100; rejected rate is separately persisted. Voided/invalid inspections are excluded and accepted + rejected must equal inspected.
- Cost: calculate the approved absolute unit-price variance score per comparable invoice line. Within a PO line, valid partial invoice quantities weight the line scores, capped at ordered quantity; then average eligible PO-line scores equally. The numerator is the sum of PO-line scores and the denominator is the eligible PO-line count. Variance/per-line score precision is 12 decimals HALF_UP; component display score is 2 decimals HALF_UP. Currency must match. Invoices and amounts must reconcile. See `component-definitions.md` for statuses, cutoff, and exclusions.
- Capacity: gross received quantity (not accepted quantity; quality is scored separately) is allocated once to eligible supplier/site/product/UOM/period commitments. Exact-site commitments have priority over supplier-wide commitments, then earliest period end, earliest period start, and stable commitment ID. Receipt quantities are deduplicated by receipt-line ID, capped at cumulative shipped quantity per shipment line, split across commitments as needed, and capped at remaining commitment quantity. Only receipts within the scoring window and known by `as_of` are considered. The score is `100 × total allocated fulfilled quantity / total eligible committed quantity`, capped at 100. Receipt periods are half-open: `period_start <= received_at < period_end + 1 day`.
- Compliance: a versioned 12-code policy map assigns nine supplier-scoped and three site-scoped requirements. Score = passed valid completed applicable checks / eligible passed-or-failed checks × 100. Pending, expired, missing, invalid, NOT_APPLICABLE, and legacy evidence with unknown availability remain separately counted and excluded from the pass/fail denominator. A mandatory critical failure or unverifiable mandatory-critical requirement is an independent escalation.
- Disruption: severity × fractional active duration in days × `0.5^(signal age in days/90)`, scaled by the snapshotted exposure limit and clamped to 0–100. Intervals use half-open boundaries; exact duplicate non-null source references are deduplicated, while distinct incidents remain independent even when overlapping. Signals with no positive active duration are excluded. A source with no records known at the cutoff is `MISSING_DATA`, not a 100 score.

Known cost limitations: invoice status history and invoice-line product/UOM fields do not exist; current status is excluded if `updated_at` is after the run cutoff, and product/UOM compatibility relies on the required PO-line foreign-key mapping. Semantic duplicate invoices with null external source references cannot be recognized. Credits, discounts, and surcharges are not represented by the operational schema. PostgreSQL runtime verification of the updated cost query and evidence persistence remains pending. Capacity uses gross receipts because the operational receipt/inspection model separates physical receiving from quality acceptance; receipt quantities are allocated only once and capped by shipped-line quantity. The schema has no direct commitment-to-PO-line relationship, so commitments are matched by supplier/site/product/UOM/period. V8 policy/scope source changes are implemented but migration execution, compliance SQL, and historical same-cutoff reproducibility still require isolated PostgreSQL verification. PO status cannot be reconstructed historically because there is no purchase-order status history; rows whose `updated_at` exceeds the cutoff are explicitly excluded.

Each run snapshots weights, observation thresholds, the coverage threshold, 90-day disruption half-life, exposure scale, and rounding policy. Event times and record creation times must both be no later than `as_of`. Historical result immutability is enforced in the database for completed runs.

# Compliance policy (Phase 4 prospective history)

Compliance is 10% of the configured weighted score. It is calculated as passed eligible requirement checks divided by eligible completed checks, multiplied by 100. It is AVAILABLE only when the configured minimum check count is met; absent, pending, expired, invalid, or evidence-less rows are excluded and reported rather than treated as passes.

Mandatory codes: BUSINESS_LICENSE, TAX_REGISTRATION, SANCTIONS_SCREEN, INSURANCE_COVER. Criticality is independent: SANCTIONS_SCREEN and INSURANCE_COVER are critical. Supplier scope: BUSINESS_LICENSE, TAX_REGISTRATION, QUALITY_CERT, ENVIRONMENT_CERT, DATA_SECURITY, ANTI_BRIBERY, SANCTIONS_SCREEN, INSURANCE_COVER, CONTINUITY_PLAN. Site scope: WORKPLACE_SAFETY, ORIGIN_DECLARATION, TRACEABILITY, for each active site.

V8 captures `transaction_timestamp()` inside the first Flyway migration transaction and uses one repeatable-read snapshot for the active-site baseline. It rejects records inconsistent with that cutover. It does not fabricate historical site, assessment-status, check, or evidence-availability events. Existing critical values must match the independent approved map or migration validation aborts. Policy/scope events are append-only; assessment/check snapshots, status events, and evidence events begin prospectively. V8 has not been applied or runtime verified.

The site lifecycle trigger appends a site scope version and requirement-to-scope applicability records in the same transaction as site insert/status/effective-date changes. The application locks supplier IDs in ascending order before multi-row site writes; the trigger locks the matching supplier for other lifecycle writers. Supplier ownership changes are rejected, and sites with scope history cannot be deleted. Scope selection uses the latest recorded version at `as_of`, then applies its effective-date interval. SQL behavior, concurrency, rollback, and migration compatibility still require isolated PostgreSQL integration verification.
