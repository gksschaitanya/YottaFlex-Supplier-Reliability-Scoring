# Score explainability

Each supplier/component result now writes compact evidence rows into the existing V7 `score_evidence` table in the same database transaction as the run's score, component, and source-observation rows. A write failure rolls all those result rows back; the run is then marked `FAILED` outside that transaction. Historical runs are not backfilled.

Evidence uses operational source records and the scoring run's `as_of` cutoff. Source types are `PO_LINE` (delivery), `INSPECTION_LINE` (quality), `INVOICE_LINE` (cost), `CAPACITY_COMMITMENT` and `RECEIPT_LINE` (capacity), `COMPLIANCE_CHECK` (compliance), and `RISK_SIGNAL` (disruption). Every row links to its score run, supplier score, component result, supplier, and source record. The business reference is compact; `details` contains calculation-relevant values. Capacity commitment evidence contains allocated fulfillment and remaining commitment quantities; receipt-line evidence traces allocations to commitments, receipts, shipment lines, purchase orders, products, and UOM. Capacity numerators reconcile from commitment evidence contributions; receipt-line rows provide source traceability. No ground-truth fields or full operational payloads are copied.

`included=true` means the operational row contributes to the current component's calculation; `included=false` identifies an excluded source and carries a reason where the source can be classified. A contribution of zero is still a contribution when the source was eligible. These evidence rows expose traceability for the current calculators; they do not change the scoring formulas or claim that every Phase 4 scoring-policy gap has been closed.

The paginated evidence endpoints return `ScoreEvidenceResponse` DTOs with run/supplier/component/source identifiers, disposition, contribution, exclusion reason, evaluation timestamp, and structured details. Filters support component, included/excluded, and source entity type. Sorting supports `evaluatedAt`, `sourceBusinessId`, `contribution`, or `sourceEntityType` with ascending/descending direction; page is zero-based and size is capped at 100.

Disruption evidence is produced from the same deterministic calculation result as the exposure numerator and component score. Each known-by-cutoff risk signal has its source record ID, risk business ID, contribution, and an explicit exclusion reason when not included. Late-recorded signals are not included in a historical run's evidence. Exact duplicate source references, invalid severities, future starts, zero-duration events, and out-of-window events remain separately identified where they were known at the cutoff.

The isolated PostgreSQL integration suite verified all six evidence types, score/run/supplier/component links, source row existence and ownership, cutoff-respecting sources, exclusion reasons, API filters/pagination, and repeat reads without writes. A trigger-injected evidence insert failure confirmed that no partial scores, components, observation counts, or evidence remain for the failed run. Earlier score runs were not backfilled.
# Compliance evidence

Compliance score evidence is produced from the same cutoff-aware result as the component metrics. Details include requirement code/id, mandatory and critical flags, supplier/site scope, assessment/status, check result, evidence availability, exclusion, and escalation reasons. Evidence remains paginated through the existing score evidence API. Missing records are represented as exclusions where a source row exists; absence-only scope cases remain a known limitation pending database verification and a dedicated scope evidence source.
